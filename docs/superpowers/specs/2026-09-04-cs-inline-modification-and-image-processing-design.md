# 客服修改沟通与款式图精细处理设计

**日期：** 2026-09-04  
**状态：** 已完成交互确认，待实施  
**范围：** 客服基础美工任务、款式图编辑器、本地批量提交与相关作品预览

## 1. 目标

本次调整解决三个相互关联的问题：

1. 改善款式图编辑器对纯白底、纯色底 Logo 和文字图片的透明底质量，并支持透明图片换色。
2. 将客服与基础美工的修改流程改为任务详情页内的多轮双向沟通记录，不再使用“新增修改”和“重新上传”弹窗。
3. 保持首次作品、修改作品、申请分数、批量提交和撤回之间的数据归属清晰，同时不改变其他角色和其他任务组的原有流程。

## 2. 不在本次范围内

- 不接入云端或本地大型 AI 抠图模型。
- 不承诺处理复杂实景背景、毛发或透明玻璃等专业抠图场景。
- 不将修改记录扩展为任意人员参与的聊天系统。
- 不改变非客服基础美工任务的驳回、审核、上传和分值逻辑。
- 不执行构建、客户端打包或远程仓库推送。

## 3. 业务术语

**首次作品**：基础美工接单后第一次完成并提交的作品。首次作品始终作为任务主体作品，展示在详情页上方“作品图片”区域，不归入修改记录。

**修改轮次**：客服对待审核作品提出一次正式修改需求，基础美工在同一条记录中提交本轮处理结果。轮次按任务内的第 1 次、第 2 次依次编号。

**当前申请分数**：任务当前保存的 `applied_score`。首次提交或任一修改轮次完成时可更新，最终以客服点击“通过”时的值为准。

**最新实际作品**：按修改轮次从新到旧寻找，最近一轮基础美工实际上传的图片；若所有修改轮次都没有图片，则为首次作品图片。

## 4. 总体方案

扩展现有 `task_reject_record` 修改记录，不新建通用会话模型。文件继续通过 `task_file.reject_record_id` 归属某一轮：

- 客服修改附件使用 `file_category = reject`。
- 基础美工修改作品使用 `file_category = work`，并绑定对应修改记录。
- 首次作品使用 `file_category = work`，但 `reject_record_id` 为空。

修改流程仍复用现有任务状态：

- `accepted`：基础美工首次待提交。
- `doing`：客服待审核。
- `rejected`：基础美工正在处理客服修改。
- `finished`：客服已经通过，任务完成。

修改沟通只在 `task_group = cs` 中启用。

## 5. 修改轮次数据

现有修改记录保留以下字段：

- `task_id`
- `reject_index`
- `reviewer_id`
- `reviewer_name`
- `reject_reason`
- `designer_reply`
- `create_time`，作为客服完成本轮需求的时间

新增以下字段：

- `designer_id`：完成本轮处理的基础美工 ID
- `designer_name`：完成本轮处理的基础美工姓名
- `designer_complete_time`：基础美工完成本轮的时间；为空表示仍等待基础美工
- `applied_score`：基础美工本轮完成时保存的申请分数快照

同一套数据库迁移同时覆盖 SQLite 和 MySQL。新增字段均允许为空或提供安全默认值，迁移不会清空或改写已有修改记录。

记录状态由 `designer_complete_time` 判定：

- 为空：等待基础美工处理。
- 非空：客服和基础美工双方均已完成本轮。

同一任务只能存在一条 `designer_complete_time` 为空的修改记录。前端控制之外，服务端在事务和任务锁中再次校验。

## 6. 客服详情页交互

### 6.1 入口位置

- 客服作品审核表格的操作列保留“查看作品”和“通过”。
- 操作列移除“新增修改”。
- 详情页顶部保留原“通过”按钮。
- “修改记录”区域固定在“已提交作品图片/附件”之后。
- “新增修改”按钮位于修改记录标题行右侧。

### 6.2 新增修改

点击“新增修改”后，在详情页内直接展开尚未保存的新一轮：

- 左侧是客服修改需求编辑区。
- 右侧显示等待基础美工处理，不允许客服编辑。
- 客服侧包含文字框、上传框和“完成”按钮。
- 上传框支持点击选择、拖拽上传，以及鼠标悬停激活后粘贴截图。
- 文字或文件至少填写一项才能完成。

在客服点击“完成”前，新一轮只存在于当前前端页面。关闭详情页将丢弃未完成内容，不创建数据库记录、不修改任务状态、不发送通知。

点击“完成”后：

1. 创建正式修改记录并保存客服附件。
2. 任务从 `doing` 变为 `rejected`。
3. 通知当前基础美工处理。
4. 本轮左侧变为只读，状态显示“等待基础美工”。

客服不能连续创建两条待处理修改。只有基础美工完成当前轮次、任务回到 `doing` 后，客服才能选择“通过”或新增下一轮。

### 6.3 折叠规则

- 修改记录按照第 1 次到第 N 次展示。
- 每一轮都可以独立折叠和展开。
- 当前未完成轮次默认展开。
- 已完成历史轮次默认折叠。
- 展开后始终是客服在左、基础美工在右，符合“需求 -> 处理结果”的阅读顺序。

## 7. 基础美工详情页交互

### 7.1 首次提交

基础美工首次接单后的“上传作品”保持现有方式和数据归属。提交的文件继续显示在详情页上方“作品图片/附件”区域，不进入修改记录。

### 7.2 处理修改

当任务处于 `rejected` 且存在待处理修改轮次时：

- 不显示独立的“重新上传作品”弹窗。
- 详情页自动展开最新待处理轮次。
- 客服左侧内容只读。
- 基础美工右侧可填写处理结果、管理作品文件、调整申请分数并点击“完成”。
- 上传框支持点击选择、拖拽上传和悬停后粘贴截图。
- 文字或文件至少一项即可完成；允许只提交文字。
- 申请分数默认带出任务当前申请分数，而不是重置为 1。

点击“完成”后：

1. 基础美工内容和文件保存到当前修改记录。
2. `designer_complete_time`、完成人和该轮分数快照更新。
3. `task_info.applied_score` 更新为本次填写的分数。
4. 任务从 `rejected` 回到 `doing`，等待客服审核。
5. 此时不进入分值审核。

## 8. 申请分数与审核

- 申请分数是任务级当前值，不要求每轮重新决定。
- 首次提交、详情页修改完成、批量提交均默认带出已有 `applied_score`；没有值时才使用 1。
- 基础美工可在任一完成动作中修改申请分数，修改后覆盖任务当前申请分数。
- 修改过程以及基础美工完成修改后都不创建待审核分值。
- 只有客服最终点击任务“通过”时才处理分值审核：
  - 最终申请分数等于 1：任务结束，不进入分值审核。
  - 最终申请分数大于 1：任务结束，并创建或更新待审核分值，审核值为最后保存的申请分数。
- 分值审核通过后的最终计分继续复用原有审核流程。

## 9. 撤回与重新编辑

基础美工在待审核任务中点击“撤回”只回退提交状态，不删除已保存内容。

### 9.1 撤回首次作品

- 任务从 `doing` 回到 `accepted`。
- 首次作品文件继续保留。
- 当前申请分数继续保留。
- 再次打开上传时带出现有文件和申请分数，允许删除、替换、增加或只调整部分内容。

### 9.2 撤回修改轮次

若任务最新一轮修改已经由基础美工完成：

- 任务从 `doing` 回到 `rejected`。
- 仍然编辑同一条修改记录，不创建新轮次。
- `designer_complete_time` 清空以重新表示“等待基础美工”，但原回复、原文件、完成人信息和申请分数均保留。
- 详情页右侧带出全部已有内容，可做局部修改。

基础美工重新编辑期间，新增文件和删除选择先保留在当前页面；关闭详情页不会覆盖上一次已经完成保存的内容。再次点击“完成”时，客户端提交“继续保留的旧文件 ID + 新文件 + 当前文字 + 当前分数”，服务端原子更新该轮结果。只有明确移除的文件才删除。

## 10. 批量提交

批量提交继续用任务编号优先、旺旺 ID 备用的现有匹配规则。

匹配结果增加提交类型：

- `首次提交`：任务为 `accepted`，提交文件归入首次作品。
- `第 N 次修改`：任务为 `rejected` 且存在唯一待处理修改，提交文件归入该修改记录，并完成基础美工右侧。

基础美工不能通过批量提交自行创建修改轮次。没有客服待处理轮次时，不能把 `rejected` 任务作为修改提交。

批量提交中的申请分数默认带出每条任务当前申请分数，允许分别调整；提交后只更新任务当前申请分数，不立即进入分值审核。服务端提交时重新校验任务状态、执行人和待处理轮次，防止匹配完成后任务已被其他操作改变。

## 11. 作品预览规则

客服和基础美工相关表格中只要存在“作品预览”列，都统一使用以下优先级：

1. 最新修改轮次中基础美工实际上传的作品图片。
2. 更早修改轮次中最近一次实际上传的作品图片。
3. 首次作品图片。

适用页面包括客服和基础美工的我的任务、待做任务、待审核任务、作品审核，以及客服基础美工全量任务中的相同预览列。

若最新轮次只填写文字，没有上传图片，则继续显示上一轮实际作品。旧轮次和首次作品不会被移动或覆盖：

- 首次作品始终显示在详情页上方“作品图片”。
- 修改作品始终显示在对应折叠轮次的基础美工右侧。

## 12. 款式图精细透明底

现有算法只将容差内的像素直接变为完全透明，容易在抗锯齿文字和 Logo 边缘留下白边或原背景色。新处理流程为：

1. 从图片四周采样并估算白底或主要纯色背景。
2. 对高置信度背景色做全图匹配，因此可以清理字体孔洞等未与图片边缘连通的背景区域。
3. 根据像素与背景色的距离生成软透明度，而不是只做全透明/不透明二选一。
4. 根据估算背景色和软透明度对边缘 RGB 去污染，减少白边和彩色底边。
5. 对极低透明度像素做稳定性保护，避免反算颜色产生噪点。

编辑器提供：

- “去底容差”：控制背景颜色匹配范围。
- “边缘净化”：控制软边缘和背景色去污染强度。
- “一键透明底”：处理当前选中的上传图片图层。
- “恢复图片”：恢复当前上传图片的原始数据。

处理仍在浏览器 Canvas 中完成，不上传第三方服务。主要目标是白底和单一纯色底 Logo、文字、图案；复杂实景背景明确不在保证范围内。

## 13. 前景换色

换色只作用于当前选中的上传图片图层，不修改素材库原图。已透明 PNG 可直接换色，无需先执行透明底。

### 13.1 整体单色

- 将全部非透明像素转换为目标颜色。
- 保留当前 Alpha，包括透明底产生的软边缘。
- 适用于单色 Logo 和文字。

### 13.2 指定颜色

- 用户点击吸管，再直接点击图片中的原颜色。
- 目标颜色通过颜色选择器设置。
- “颜色容差”控制相近颜色的匹配范围。
- 替换强度根据颜色距离平滑过渡，避免匹配边缘形成硬色块。
- 非匹配颜色保持不变。

透明底、整体换色、指定颜色换色都进入编辑器现有的撤销/恢复历史。界面同时保留“撤销换色”“恢复图片”和底部“还原原图”，各自作用范围清晰。

## 14. 组件边界

- `StyleImageEditor` 只负责编辑器交互、Canvas 图层和历史记录。
- 背景识别、软透明、边缘去色、吸管采样和颜色替换放入纯函数工具模块，便于使用合成像素测试，不与 Fabric.js UI 耦合。
- 修改记录展示和编辑收敛到客服任务专用组件，内部负责折叠、左右栏、上传暂存和完成状态。
- 通用 `TaskDetail` 只提供固定插入位置和数据/事件边界，不直接调用修改业务 API。
- 客服作品审核页面负责客服完成修改和最终通过。
- 基础美工任务页面负责修改回复、撤回和再次完成。
- 批量提交服务负责解析匹配类型，实际提交仍调用服务端统一的任务状态校验和文件持久化逻辑。

这样可以保证其他角色继续复用通用详情外壳，但不会得到客服修改专用操作。

## 15. 权限与并发保护

- 只有任务发布客服可以完成客服修改需求。
- 只有任务当前分配的基础美工可以完成或撤回基础美工处理结果。
- 管理员查看客服全量任务时可读取完整修改记录，但不默认代替双方完成修改。
- 客服最终通过前，服务端确认不存在未完成修改轮次。
- 创建轮次、完成轮次、撤回和最终通过均复用任务级锁，并在数据库事务内检查最新任务状态。
- 重复点击、过期页面、错误角色、非最新轮次和状态已变化的请求返回明确业务错误，不部分写入数据。

## 16. 文件一致性与错误处理

- 新文件先进入现有受控上传流程，数据库提交失败时清理本次新增的未关联文件。
- 再编辑时的旧文件删除在成功提交新记录状态后执行，避免请求失败导致旧内容丢失。
- 文件上传失败、分数非法、文字和文件均为空时，任务状态和已有轮次保持不变。
- 列表预览无法加载某张图时仍可回退到同一轮其他图片或更早实际作品，不修改业务数据。
- 图片处理异常时保留当前图层之前的图像和历史记录，用户可以重试、撤销或恢复图片。

### 17.1 图片算法单元验证

- 白底和单一彩色底识别。
- 字体孔洞等内部背景清理。
- 抗锯齿边缘生成渐变透明度。
- 白边和彩色背景污染降低。
- 整体单色保留 Alpha。
- 吸管采样和指定颜色容差替换。
- 非匹配颜色不变化。

### 17.2 后端流程验证

- 首次提交不提前创建分值审核。
- 客服完成修改需求后创建唯一待处理轮次。
- 重复或并行创建修改被拒绝。
- 基础美工以文字、文件或两者完成轮次。
- 修改期间更新申请分数但不进入分值审核。
- 客服最终通过时按照最后申请分数决定是否进入分值审核。
- 首次作品撤回保留文件和分数。
- 修改轮次撤回保留同一轮文字、文件和分数。
- 批量提交正确区分首次提交与第 N 次修改。
- 错误角色、错误任务状态和过期轮次不会写入部分数据。

### 17.3 页面验证

- 关闭未完成客服修改不会创建记录。
- 基础美工撤回后重新打开仍带出完整内容。
- 批量提交显示“首次提交”或“第 N 次修改”。
