# Electron 原生文件拖拽缓存优化设计

## 背景与根因

当前 Electron 客户端使用 `webContents.startDrag()` 把真实本地文件交给桌面、企业微信和 Photoshop。任务文件通常只存在于服务器，拖拽前必须先下载到本地临时目录。

现有流程在拖拽开始时同步检查缓存；如果文件尚未下载，就异步请求 `/api/task/download/:fileId`，写入临时文件，并提示“文件正在准备，请稍后再拖拽”。因此第一次拖拽会等待完整文件下载。当前主进程对同一个 IPC 请求中的多个文件按顺序下载，且缓存索引只保存在内存中，Electron 重启后会丢失索引，即使临时文件仍存在也会再次下载。

这不是原生拖拽能力不可用，而是本地文件准备时机过晚、并发和缓存复用不足造成的延迟。

## 目标

- 文件在列表或详情中可见并完成加载后，后台尽早准备本地拖拽文件。
- 已准备好的文件在拖拽开始时直接调用同步 `startDrag`，不再等待接口。
- 同一文件和同一拖出文件名不重复下载；Electron 重启后尽量复用仍有效的临时缓存。
- 多文件预加载采用有限并发，避免当前串行下载造成长时间等待。
- 客服、基础美工继续使用任务编号加原扩展名命名；其他角色继续使用原上传文件名。
- Electron 中缓存未完成时不向外部软件发送带 token 的接口 URL。
- 不修改服务器文件名、数据库数据、任务状态、权限、上传接口和任务流转。

## 非目标

- 不实现 Windows 虚拟文件提供器。
- 不把服务器文件永久复制到任务上传目录。
- 不改变浏览器网页版的 URL 拖拽降级行为。
- 不修改服务端 API 协议或数据库结构。

## 设计

### 1. Renderer 端准备队列

`src/api/upload.js` 继续作为拖拽入口和命名策略的唯一来源。

- `registerDragFileUrl()` 在文件 URL 注册时触发后台预加载，图片加载完成后的现有注册路径继续生效。
- 预加载任务使用 `fileId + resolvedFileName + downloadPath` 作为去重键，避免原文件名和任务编号命名互相抑制。
- `preloadFilesForDrag()` 只发送有效文件，并保留现有下载路径；页面销毁不取消已开始的单文件准备，以提高再次进入页面时的命中率。
- 拖拽开始前通过同步 `isFileCached()` 判断；命中后立即调用 `doFileDrag({ fileId })`。
- 未命中时保留现有“正在准备”提示，但不写入任何 URL、HTML 或文本拖拽数据。

### 2. Main 端磁盘缓存

`electron/main.js` 继续使用 `app.getPath('temp')/nexus-drag`，不写入服务器上传目录。

- 缓存文件使用安全文件名，并保留现有重名后缀规则。
- 新增轻量 `manifest.json`，记录 `fileId`、逻辑文件名、下载路径、临时文件路径、文件大小和更新时间。
- Electron 启动或首次检查时从 manifest 恢复内存索引；缓存文件存在、文件名/下载路径匹配且更新时间不超过 1 小时才视为有效，否则删除索引并重新准备。
- manifest 写入采用临时文件替换，避免进程中断留下半写状态。
- 继续保留现有过期清理机制，清理文件时同步清理 manifest 条目。

### 3. 有限并发与优先级

- 主进程维护按缓存键去重的准备任务表；同一文件只能有一个下载任务，后续请求复用该 Promise。
- 多文件准备最多并行 3 个下载任务。
- 当前拖拽目标的准备请求具有高优先级；如果该文件已在低优先级队列中，提升其优先级而不是重复下载。IPC item 增加 `priority` 字段，普通预加载为 `normal`，拖拽瞬间重试为 `high`。
- 单文件下载失败只影响该文件，并清理不完整临时文件；下次请求可以重新尝试。
- 不为拖拽增加长轮询或阻塞 renderer 的同步网络请求。

### 4. 文件命名与兼容性

- 客服和基础美工：`任务编号.原扩展名`，同一任务的后续文件继续使用稳定的 `_1`、`_2` 后缀。
- 运营、运营助理、美工设计师、管理员及其他页面：继续使用服务端原始 `file_name`，仅清理 Windows 非法字符。
- manifest 只保存客户端缓存元数据，不改变服务端 `task_file.file_name`。
- `do-file-drag` 同时兼容旧的标量 `fileId` 调用和当前 `{ fileId }` 请求，避免其他页面回归。

## 数据流

```text
页面渲染/图片加载
  -> registerDragFileUrl(file)
  -> renderer 去重队列
  -> prepare-file-drags IPC
  -> main 端 manifest/磁盘缓存检查
  -> 最多 3 路下载并写入临时文件

用户 dragstart
  -> 同步 is-file-cached(fileId, resolvedName)
  -> 命中: do-file-drag({ fileId }) -> webContents.startDrag(localPath)
  -> 未命中: 取消 URL 数据，提示稍后重试
```

## 错误处理

- token 缺失、HTTP 错误、文件不存在或写入失败时记录现有日志格式，并删除本次不完整缓存。
- 下载失败不会把错误 URL 传给外部软件；用户再次拖拽时允许重新准备。
- manifest 损坏时忽略并重建，不影响任务数据和应用启动。
- 缓存目录不可写时保留现有提示和下载按钮作为人工兜底。

## 验收标准

1. 正常网络下，列表图片显示后拖到桌面、企业微信和 Photoshop，不再因为首次拖拽才开始下载而出现明显等待。
2. 同一文件第二次拖拽直接成功；关闭并重新打开 Electron 后，仍存在且匹配的缓存可以直接复用。
3. 同一任务的多个文件名称仍按任务编号、扩展名和 `_1`、`_2` 规则生成。
4. 其他角色拖出文件仍保持原上传文件名。
5. 缓存未完成、下载失败和缓存损坏时，Electron 不产生带 token 的 URL/文本拖拽数据。
6. 现有浏览器拖拽测试、后端测试和任务页面功能不受影响。

## 影响范围

- 前端：`src/api/upload.js`，负责文件注册、去重键、普通/高优先级预加载和拖拽命名。
- Electron：`electron/main.js`、`electron/preload.js`，负责 manifest、磁盘缓存、有限并发队列和同步原生拖拽。
- 测试：扩展现有 `tests/task-pages/task-page-features.spec.js` 的缓存复用、并发去重和未命中行为测试；不新增生产数据库或服务端测试。
