# 店长身份、受限开启打款与付费审核设计

日期：2026-08-31

## 背景与目标

现有系统只有运营角色默认拥有运营美工作品审核页面；`payment.open` 只控制页面内的“开启打款”按钮，无法让其他角色独立进入页面处理同店铺任务。打款流程第二阶段的“店长付费确认”由旧操作权限 `payment.manager_review` 控制，但系统没有正式的店长身份、待审核队列或多人审核并发保护。

本次调整目标：

- 为运营和运营助理增加明确的店铺及店长身份。
- 让 `payment.open` 独立提供受限版作品审核页面，不附带任务审核权。
- 非店长提交第一阶段后进入同店铺店长的正式付费审核流程。
- 子管理员默认跨店铺只读并可审核全部店铺，但不默认获得编辑、删除等完整管理权。
- 保持运营助理原任务全流程、运营美工任务状态流转和现有打款时间线不受影响。

## 范围外事项

- 不按店铺隔离运营助理原有任务大厅、接单、提交、转移和审核流程。
- 不改变运营美工任务的创建、接单、上传、通过、驳回和完成状态规则。
- 不增加店长审核历史页面；店长审核页只承载当前待办。
- 不修改打款记录现有时间线展示形式，只增加待审核状态和第二阶段结束原因。
- 不执行前端、Electron 或安装包打包。
- 不连接或修改生产数据库，不推送远程仓库。

## 总体方案

采用独立的店长待审核队列表。队列表只保存当前有效的待办申请，不承担历史展示。审核通过或拒绝后，审核结果写回原打款记录并立即删除待办；操作人和时间写入现有系统操作日志。拒绝后恢复流程时重新创建一条新待办。

账号身份、任务审核能力、开启打款能力和打款数据范围分别判断：

```text
账号角色/店铺/店长身份
  -> 决定店长审核资格和同店铺范围

原任务审核权限 + 是否为原发布人
  -> 决定能否通过/驳回运营美工作品

payment.open
  -> 决定能否进入受限作品审核页面并开启打款

打款页面/操作权限
  -> 决定选品收集和打款记录的查看、编辑、删除、恢复、重开
```

## 账号身份模型

### 运营角色

- 店铺继续为必填的单选项。
- 新增“是否为店长”选项，使用是/否开关，默认否。
- 店长身份只影响打款跟踪和店长审核，不改变运营原有任务权限。

### 运营助理角色

- 新增店铺单选项并设为必填。
- 新增“是否为店长”选项，默认否。
- 现有运营助理账号升级后店铺保持空值，由超级管理员逐个配置，不自动推断。
- 未配置店铺前，账号仍可使用原运营助理任务流程，但不能使用依赖同店铺范围的开启打款或店长审核能力。

### 其他角色

- 其他普通角色不显示店铺和店长选项。
- 账号从运营或运营助理改为其他角色时，清空店铺和店长身份，避免残留身份继续生效。
- 子管理员和超级管理员不显示店长开关，系统直接视为全店铺店长。
- `payment.manage.all` 持有人视为全店铺管理身份，不要求绑定店铺。

### 登录态

- 用户登录信息和访问令牌增加店长身份字段。
- 新增、修改店铺或店长身份后撤销该用户刷新令牌，要求重新登录后完全生效。
- 前端显示只用于交互；所有身份和店铺范围必须由后端再次校验。

## 运营助理原任务流程兼容

运营助理新增店铺字段不得参与原任务流程的数据查询或操作校验。以下行为继续只按角色、原任务权限、任务分区和接单人判断：

- 运营助理任务大厅。
- 我的任务、待做任务、待审核任务。
- 运营发布运营助理任务及指定运营助理。
- 接单、上传凭证、提交完成、撤回提交。
- 任务转移和任务审核。

运营发布任务时仍可选择所有符合现有规则的运营助理，不按新增店铺过滤。相关查询、服务和接口必须加入回归测试，防止新增店铺条件被误复用到原任务 DAO。

## 权限调整

### 移除旧店长权限

- 从权限目录和权限配置页面移除 `payment.manager_review`（店长审核准备工作）。
- 删除用户已有的该权限覆盖配置。
- 店长付费审核资格不再由可配置操作权限决定。
- 不根据旧权限自动把账号迁移为店长，统一以用户管理中的店长身份为准。

### 全店铺只读权限

新增 `payment.view.all`（查看全部店铺打款数据）：

- 可以查看全部店铺的进行中选品记录和已结束打款记录。
- 自动提供选品收集和打款记录页面入口。
- 不允许新增、编辑、保存阶段、推进、结束、删除、恢复、重开、上传或删除图片。
- 默认授予子管理员和超级管理员。
- `payment.manage.all` 自动包含该只读能力，但继续拥有全部操作权。

子管理员的默认能力为“跨店铺只读 + 全店铺店长审核”，不默认包含 `payment.manage.all`、`payment.open` 或其他打款操作权限。

### 店长审核入口

- 运营店长和运营助理店长自动获得“店长审核”入口和同店铺待办只读权。
- 子管理员、超级管理员和 `payment.manage.all` 持有人自动获得全店铺店长审核入口。
- 店长身份不自动赋予选品编辑、删除、恢复、重开或开启打款权限。
- 没有选品收集页面权限的店长仍可从审核页只读查看待审核记录。

## 作品审核与开启打款

### 页面入口

运营美工“作品审核”页面满足任一条件即可进入：

- 拥有原 `operator.review.design` 权限。
- 拥有 `payment.open` 权限。

`payment.open` 只提供受限页面能力，不隐含 `task.review.own`、`task.review.store` 或 `task.review.all`。

### 数据范围

- 仅有 `payment.open` 的普通账号可查看同店铺所有已提交待审核的运营美工任务。
- 不混入运营助理任务或客服基础美工任务。
- 子管理员、超级管理员或 `payment.manage.all` 持有人在拥有 `payment.open` 时按全店铺范围查询。
- 没有店铺的普通账号不能查询同店铺任务，返回明确配置提示。

### 逐条操作

每条任务独立计算可用动作：

- 当前用户是原任务发布人，或原任务权限允许其审核：保持查看作品、通过、驳回等原能力。
- 同店铺但不是原发布人且没有任务审核权：只能查看作品、开启打款。
- 开启打款仍要求 `payment.open`，并沿用作品图片、任务状态和重复开启校验。
- 查看作品详情的同店铺放行只适用于受限开启打款场景，不能扩展成其他任务编辑或审核能力。
- 后端接口执行相同的逐任务校验，不能依赖隐藏按钮保证安全。

开启打款继续只创建或恢复选品记录，复制来源任务款号、发布时间和作品图片，不修改原任务状态或任务流转。

### 批量操作

- 页面保留一套行选择框。
- “批量审核通过”只统计和处理选中任务中当前用户真正可审核的记录。
- “批量开启打款”只统计和处理选中任务中当前用户可开启的记录。
- 两个按钮分别显示可处理数量，不使用选中总数造成误导。
- 已开启、无作品图片或其他不符合条件的任务继续按现有规则跳过并展示原因。
- 批量审核不能因为同一批次包含不可审核任务而越权处理这些任务。

### 页面与详情

- 可审核任务显示“查看作品、通过、驳回、开启打款”。
- 仅可开启打款的任务显示“查看作品、开启打款”。
- 详情弹窗使用与列表一致的动作判断。
- 图片预览、拖拽、下载和现有详情字段保持不变。

## 店长付费审核流程

### 提交第一阶段

非店长、非子管理员、非超级管理员且不具备 `payment.manage.all` 的用户完成“信息及选品”并点击进入下一阶段时：

1. 校验并保存第一阶段数据和产品主图。
2. 完成第一阶段，创建第二阶段节点。
3. 创建当前店铺的店长待审核申请。
4. 记录进入“第二阶段 · 待店长审核”。

第二阶段待审核期间：

- 填写人可以只读查看记录。
- 第二阶段表单、保存、结束、进入下一阶段和历史阶段重开均锁定。
- 选品收集卡片和第二阶段详情顶部显示“待店长审核”。
- 删除原记录时同步删除待审核申请。

### 无需申请的人员

店长、子管理员、超级管理员或 `payment.manage.all` 持有人提交第一阶段时，直接进入正常第二阶段，不创建待审核申请。“确认开启付费”和“付费时间”保持当前手动选择方式。

是否需要审核按执行“进入下一阶段”的当前用户身份判断，不根据记录策划人推测当前操作者。

### 店长审核页面

“店长审核”位于“打款跟踪”分区，排列在“选品收集”和“打款记录”之间：

- 页面只展示当前待审核申请。
- 普通店长只看记录所属店铺。
- 子管理员、超级管理员和 `payment.manage.all` 持有人看全部店铺。
- 提供店铺、申请人、申请时间等必要筛选；操作列只有“查看记录、通过、拒绝”。
- 查看记录为只读，可查看第一阶段字段、阶段图片和来源任务。
- 菜单显示红色待办数量；新申请同时写入通知中心，不弹出强制模态框打断当前工作。

### 审核通过

- 点击“通过”打开付费时间选择弹窗。
- 付费时间必填，使用现有日期时间格式。
- 提交后写入第二阶段 `paid_enabled = 1` 和付费时间。
- 删除当前待审核申请，解除第二阶段锁定。
- 填写人收到通过通知，可以继续填写推广信息和后续字段。

### 审核拒绝

- 点击“拒绝”只做二次确认，不要求填写原因。
- 写入第二阶段 `paid_enabled = 0`，付费时间为空。
- 第二阶段节点标记结束，原流程以“店长未确认开启付费”结束。
- 删除当前待审核申请并通知填写人。
- 结束记录正常进入打款记录，沿用现有时间线样式并显示结束阶段和固定原因。

### 多店长并发

- 同店铺允许存在多名运营店长和运营助理店长。
- 同一待办同时显示给所有同店铺店长以及全店铺审核人。
- 第一位成功提交结果的审核人生效。
- 其他人随后操作时收到“该申请已处理”，页面刷新后待办消失。
- 审核结果、阶段变化、版本更新和待办删除必须在同一事务中完成。

### 拒绝后恢复

因“店长未确认开启付费”结束的流程恢复时：

- 保留第一阶段全部字段、图片和来源任务信息。
- 清空上一次 `paid_enabled = 0` 和付费时间。
- 第二阶段重新进入待店长审核状态。
- 创建一条新的当前待办并重新通知审核人。
- 上一次申请不恢复，也不在店长审核页面显示。

## 店长待审核队列

新增独立待审核队列表，一条选品记录最多存在一条当前待办。建议字段：

- 主键。
- `record_id`，唯一关联选品记录。
- `store`，使用记录所属店铺作为审核范围快照。
- `applicant_id` 和申请人名称快照。
- `request_version`，用于并发和重复处理校验。
- 创建时间。

队列表不保存已通过或已拒绝状态。处理完成后删除当前行；实际结果存在第二阶段和主记录中，审核人、审核时间和操作结果写入 `sys_oper_log`。通知中心只负责提醒，不作为审核状态来源。

## 数据展示与允许动作

选品记录接口新增待审核标识，并根据记录、当前用户和权限返回允许动作：

- 待审核时所有编辑、推进、结束和重开动作均为否。
- 只读全店铺用户只能查看，所有写动作均为否。
- 店长审核页的通过/拒绝资格独立计算，不复用选品编辑权限。
- `payment.manage.all` 继续拥有全部店铺正常记录的完整动作；遇到待审核记录时仍通过正式审核接口处理付费决定。

列表店铺筛选对 `payment.view.all`、`payment.manage.all`、子管理员和超级管理员显示。普通用户即使手工提交其他店铺参数，后端仍固定使用本人店铺。

## 用户管理页面

- 用户列表“店铺/组长”列调整为可同时表达运营/运营助理店铺和店长身份。
- 新增/编辑用户时，运营与运营助理显示店铺选择和“是否为店长”。
- 店铺未选时不能保存新的运营或运营助理账号。
- 编辑旧运营助理时允许页面打开并显示空店铺，但保存前要求补选。
- 店长身份默认为否；切换角色时清理不适用字段。
- 保存后提示该用户重新登录。

## 数据库迁移

迁移同时支持本地 SQLite 和生产 MySQL，通过现有后端启动迁移机制自动执行，必须幂等。

迁移步骤：

1. 为 `sys_user` 增加 `is_store_manager`，默认 `0`。
2. 创建店长待审核队列表及 `record_id` 唯一约束、店铺和创建时间索引。
3. 注册 `payment.view.all` 并加入子管理员默认权限。
4. 让 `payment.manage.all` 包含 `payment.view.all`。
5. 删除 `payment.manager_review` 的用户覆盖记录和权限目录记录。
6. 为当前处于第二阶段、流程进行中且 `paid_enabled` 为空的旧记录创建待审核申请。
7. 已有 `paid_enabled = 1` 或 `0` 的记录保持原样，不自动结束或改写。

旧运营和运营助理不会根据旧权限自动变成店长。旧运营助理店铺不回填。第一阶段、第三阶段、总结阶段、图片、来源任务和时间线数据均不修改。

如果迁移失败，后端不得在半迁移结构上继续提供相关功能；错误日志需包含具体迁移步骤和数据库错误。

## 接口与模块边界

- 用户服务负责店铺、店长身份的保存、验证和登录态映射。
- 任务查询服务提供“开启打款受限视图”，不改变原 `queryMyPublished` 的其他消费者行为。
- 任务动作服务继续独立校验原发布人和任务审核权限，`payment.open` 不进入审核授权判断。
- 开启打款服务继续负责来源任务复制和店铺校验。
- 店长审核服务负责待办列表、详情、通过、拒绝、多人并发和恢复再申请。
- 打款工作流服务负责第一阶段提交时决定直接进入或待审核，并负责拒绝结束快照。
- 打款记录服务负责只读全店铺范围、待审核标识和允许动作。
- 通知服务只在事务完成后发送提醒；通知失败不回滚已完成的业务事务。
- 侧边栏待办统计使用独立只读查询，不把通知已读状态当成待审核数量。

## 错误处理

- 普通运营助理未配置店铺却使用同店铺功能：提示先联系管理员配置店铺。
- 店铺没有本地店长：申请保持待审核，子管理员和超级管理员仍可处理。
- 非同店铺普通店长访问申请：返回 403，不泄露记录内容。
- 非店长直接调用审核接口：返回 403。
- 待办已被处理、记录版本变化或流程状态不再匹配：返回明确冲突提示并刷新列表。
- 通过时未选择付费时间：拒绝提交，不改变待办和原记录。
- 审核事务失败：原记录、阶段和待办均保持处理前状态。
- 通知发送失败：记录错误日志，但不撤销已经提交的审核结果。
- 受限作品审核用户尝试审核他人任务：返回 403，不改变任务状态。
- 只读全店铺用户尝试修改打款数据：返回 403。

## 验证标准

### 用户身份

- 运营和运营助理新增、编辑时正确校验店铺和店长身份。
- 现有运营助理空店铺数据可正常登录并使用原任务功能。
- 角色切换清理不适用的店铺和店长身份。
- 登录和刷新令牌正确携带店长身份，修改后重新登录生效。

### 运营助理回归

- 任务大厅、我的任务、待做、待审核数据范围与改动前一致。
- 发布、指定、接单、上传、提交、转移和审核不受运营助理店铺影响。
- 不新增任何针对运营助理原任务流的店铺 SQL 条件。

### 受限作品审核

- 只有 `payment.open` 的用户能进入作品审核页并看到同店铺运营美工待审核任务。
- 同店铺他人任务只有查看作品和开启打款，不能通过或驳回。
- 自己发布或原本可审核的任务保持完整原操作。
- 混合勾选时批量审核只处理可审核子集，批量开启只处理可开启子集。
- 后端拒绝跨店铺开启和越权任务审核。
- 开启打款不改变原任务状态。

### 店长审核

- 非店长提交第一阶段后进入第二阶段待审核并锁定编辑。
- 店长、子管理员、超级管理员和 `payment.manage.all` 持有人提交时直接进入正常第二阶段。
- 普通店长只看同店铺；子管理员、超级管理员看全部店铺。
- 通过必须选择付费时间并正确解锁第二阶段。
- 拒绝无需原因并以固定原因结束于第二阶段。
- 多名店长并发时只有一人成功。
- 处理后待办立即消失，店长审核页不展示历史。
- 拒绝后恢复会清空上次结果并创建新待办。
- 删除待审核记录会同步移除待办。

### 权限与数据范围

- 子管理员默认跨店铺只读并可全店铺审核，但不能新增、编辑、删除、恢复或重开。
- 超级管理员和 `payment.manage.all` 保持完整管理能力。
- 店长身份不会意外附带其他打款操作权限。
- 移除旧 `payment.manager_review` 后不存在通过旧权限绕过店长身份的路径。

### 迁移与执行限制

- 本地 SQLite 新库和旧库均可自动创建或升级结构，重复启动幂等。
- MySQL 迁移语句与 SQLite 行为一致。
- 旧第二阶段空付费确认记录生成当前待办，其他旧记录不被改写。
- 验证只使用本地数据库和本地前后端。
- 不执行 `npm run build`、Vite build、Electron build 或安装包打包命令。
- 不推送远程仓库。
