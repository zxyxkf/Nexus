# 打款跟踪启动迁移安全修复设计

## 目标

保留后端启动时自动建表、补字段和兼容旧流程数据的能力，同时保证生产 MySQL 可以执行迁移，并且后续重启不会清空有效推广方式或替用户选择第三阶段链接状态。

## 根因

- 阶段迁移在更新 `payment_selection_stage` 时从同一目标表的子查询取数，违反 MySQL 目标表更新限制。
- `promotion_method` 仍是当前第二阶段有效字段，却被放入“已移除字段清理”。
- 旧版 `abandoned` 转换把所有空白 `link_status` 都解释为旧数据，其中包括新流程尚未选择的正常空值。
- 数据清理没有独立迁移标记，因而每次启动都会执行。

## 设计

1. MySQL 模式使用目标行与旧阶段行的自连接更新；SQLite 保留现有兼容 SQL。迁移后的阶段状态和原有流程含义不变。
2. 新增一次性工作流数据迁移标记。表结构检查仍在每次启动运行，旧字段清理和旧状态转换只在标记不存在时执行，全部成功后才写入标记。
3. `promotion_method` 从旧字段清理中移除；管理员配置选项和每条记录已选值都不受启动影响。
4. 旧链接状态只转换有确定业务证据的记录：`abandoned = 1` 转为 `protect_roi`；第三阶段已经完成的旧记录转为 `keep_breaking`。当前第三阶段的空白值保持空白。

## 验证

- 现有迁移测试连续执行两次，确认推广方式和空白链接状态不变、旧放弃记录仍能转换。
- 使用捕获 SQL 的 MySQL 模式测试确认同表更新使用 `JOIN`，不再生成目标表子查询。
- 运行打款跟踪后端测试和完整后端 Jest 测试；不构建、不打包。
