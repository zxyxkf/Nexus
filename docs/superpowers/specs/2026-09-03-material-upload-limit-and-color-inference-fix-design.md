# 素材库上传限制与颜色识别修复设计

## 背景

素材库上传路由在模块加载时创建 Multer 实例。此时数据库配置尚未载入，`upload.max_file_count` 被固定为默认值 `10`。之后管理员把配置改为 `100`，运行时缓存虽然更新，既有 Multer 实例仍使用 `10`，导致一次拖入 11 张以上图片时抛出 `LIMIT_FILE_COUNT`，并被全局错误处理器转换为“服务器内部错误”。

当前颜色识别把文件名前 1 至 8 个连续中文字符直接视为颜色，因此 `图片.png` 会被错误识别成颜色“图片”。

## 修复范围

1. 素材库上传中间件在每次请求到达时创建，并读取当前 `upload.max_file_count` 与 `upload.max_file_size_mb`。
2. 配置为 `100` 时，一次上传最多允许 100 个文件，不自动分批绕过管理员设置的单次限制。
3. 将 Multer 的文件数量和单文件大小错误转换为明确的 400 业务响应；数量提示包含当前配置值。
4. 保持素材库原有图片类型过滤、文件顺序、原始文件名、重复文件名处理与数据库写入逻辑不变。
5. 颜色自动识别采用保守规则：中文前缀必须具有可识别的颜色结尾或属于常见无后缀颜色名，才作为颜色保存。
6. `军绿色A.jpg`、`樱花粉.png`、`宝石蓝A.png` 等继续自动识别；`图片.png`、`照片1.jpg`、`商品图A.png` 等返回空颜色。
7. 人工修正的颜色不受自动识别规则影响；不批量修改已有素材数据。

## 验证

- API 集成测试先把 `upload.max_file_count` 从默认值改为较小值，再验证上传中间件立即采用新值。
- 超出当前限制时返回业务码 400 和清晰提示，不返回 HTTP 500。
- 单元测试覆盖常见颜色名和通用图片名。
- 运行素材库相关测试、后端完整测试、语法检查和 `git diff --check`。
- 不执行前端构建或客户端打包。
