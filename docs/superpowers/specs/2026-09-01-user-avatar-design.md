# 用户头像修改功能设计

## 状态

- 设计日期：2026-09-01
- 状态：已确认
- 实施限制：仅在本地开发和验证，不打包、不推送远程仓库

## 背景

当前右上角用户区域、用户下拉菜单和“个人信息”弹窗均使用姓名或用户名首字作为圆形头像。用户需要能够在“个人信息”中自行选择并裁剪头像，保存后立即同步到这三个位置。头像必须存放在独立目录中，该目录由超级管理员通过系统配置维护。

## 范围

本次包含：

- 每个已登录用户上传和替换自己的头像。
- 在“个人信息”弹窗中点击头像进入图片选择和裁剪。
- 圆形裁剪遮罩、拖动、缩放和圆形结果预览。
- 右上角、下拉菜单和“个人信息”三个位置共用并即时显示当前头像。
- 新增独立头像存储目录配置。
- 本地 SQLite 和生产 MySQL 启动时自动补充所需字段和配置。

本次不包含：

- 修改用户名、姓名、角色或其他个人资料。
- 删除头像或恢复姓名首字头像的操作。
- 管理员替其他用户修改头像。
- 在任务页面、用户列表或其他人员信息位置展示头像。
- 修改现有任务、审核、权限或打款跟踪流程。

## 交互设计

### 入口

右上角用户下拉菜单保持现有结构，不增加独立“修改头像”菜单项。用户进入“个人信息”后，可以点击圆形头像或其悬浮时出现的相机图标和“修改头像”提示。

### 裁剪流程

1. 用户点击头像并选择 JPG、PNG 或 WebP 图片。
2. 系统打开独立裁剪弹窗，以圆形遮罩标示最终可见范围。
3. 用户可以拖动图片并缩放，同时查看圆形结果预览。
4. 点击“保存头像”后，前端生成标准尺寸的裁剪结果并上传。
5. 上传成功后，右上角、下拉菜单和“个人信息”中的头像立即同步，无需重新登录。
6. 关闭裁剪弹窗或上传失败时，不修改当前头像。

用户从未上传头像，或头像文件意外缺失时，界面自动回退到当前的姓名首字圆形头像。系统不提供主动删除头像或恢复默认头像的入口。

## 前端设计

### 组件边界

- `UserAvatar`：统一渲染圆形图片头像或姓名首字回退内容，供三个展示位置复用。
- `AvatarCropDialog`：管理文件选择、圆形遮罩、拖动缩放、预览和裁剪结果生成。
- 用户 Store：在一次页面会话中保存当前头像的 Object URL 和加载状态，三个展示位置不得各自重复请求头像。
- API 层：提供当前头像读取与上传方法，不让页面直接处理服务器路径。

裁剪使用成熟的图片裁剪库，不手写缩放和边界计算。前端输出 `512 x 512` 的方形图像数据；界面始终以圆形显示，因此不会把圆形边缘写入文件，也不会产生重复缩放造成的模糊。

### 状态更新

Layout 初始化后加载一次当前头像。如果后端返回无头像或文件缺失，Store 使用首字回退状态。上传成功后，Store 释放旧的 Object URL，重新读取头像并一次性驱动三个展示位置更新。组件卸载或用户退出时释放 Object URL，避免浏览器内存泄漏。

## 后端设计

### 数据模型

在 `sys_user` 中增加可空或默认为空字符串的 `avatar_path` 字段。该字段只保存头像目录下的相对文件名，不保存磁盘绝对路径，也不把图片二进制写入数据库。

在 `sys_config` 中增加：

| 配置键 | 分组 | 说明 | 可编辑 |
| --- | --- | --- | --- |
| `upload.user_avatar_dir` | `upload` | 用户头像存储目录 | 是，仅超级管理员 |

生产环境默认目录遵循现有主机上传目录规则，例如 `/app/host-uploads/user/avatars`。本地开发环境使用本地开发上传目录，确保不会读写生产服务器目录。

### API

- `GET /api/user/avatar`：登录用户读取自己的当前头像。存在时返回图片字节；未设置或文件缺失时返回明确的无头像结果，由前端显示首字头像。
- `POST /api/user/avatar`：登录用户上传裁剪后的单张头像。后端始终以 `req.user.id` 作为目标用户，不接受客户端指定其他用户 ID。

图片响应通过现有认证请求读取，不在数据库响应或前端代码中暴露服务器实际磁盘路径。

### 图片处理与校验

- 仅接受 JPG、PNG 和 WebP 源类型。
- 用户选择的源图片最大 `20 MB`，宽或高均不得超过 `12000` 像素；裁剪后的上传数据最大 `5 MB`。
- 同时检查 MIME、文件签名并实际解码图片，不能只依赖扩展名。
- 后端重新编码为 `512 x 512` WebP，移除 EXIF 等元数据。
- 文件名由用户 ID 与随机值组成，不使用原文件名，不允许路径穿越。

### 原子替换

头像替换顺序如下：

1. 在当前配置目录中写入新的临时文件。
2. 完成图片校验和重新编码。
3. 将新文件原子改名为正式文件。
4. 在数据库事务中把当前用户的 `avatar_path` 更新为新相对路径。
5. 数据库提交成功后删除旧头像。

在正式文件写入或数据库更新失败时，删除本次新文件并保留旧头像。旧头像清理失败只记录服务端警告，不撤销已经成功的新头像。

## 存储目录配置

`upload.user_avatar_dir` 复用现有上传目录配置缓存和刷新机制，但头像目录切换增加数据保护：

1. 校验新目录路径并确认可创建、可写。
2. 将数据库当前引用的所有头像从旧目录复制到新目录。
3. 校验所有引用文件均已成功复制。
4. 更新 `sys_config` 并刷新存储配置缓存。
5. 保留旧目录文件，不自动删除，以便失败恢复和人工确认。

任何复制失败都会终止配置更新，系统继续使用旧目录。这样修改配置不会使已有头像突然失效。

## 数据库初始化

数据库初始化以幂等方式完成两项工作：

- 检查并补充 `sys_user.avatar_path`。
- 使用数据库对应的忽略重复插入语法补充 `upload.user_avatar_dir`。

本地 SQLite 与生产 MySQL 使用相同字段语义。生产服务器更新并启动后会自动完成初始化，不要求管理员手动执行 SQL；本地开发只操作本地 SQLite。

## 错误处理

- 文件类型或内容不合法：拒绝上传并提示选择 JPG、PNG 或 WebP。
- 图片损坏、尺寸或体积超限：提示具体原因，保留旧头像。
- 头像目录不存在但可创建：自动创建后继续。
- 头像目录不可写：上传或配置更新失败并提示目录不可用。
- 数据库更新失败：删除新文件并继续显示旧头像。
- 已配置头像文件缺失：记录服务端警告，前端回退首字头像，不影响登录和页面访问。
- 同一用户连续上传：以后端最后一次成功提交的头像为准，不能误删当前引用文件。

## 安全与权限

- 头像读取和上传接口都要求登录。
- 上传接口只允许操作当前认证用户。
- 存储路径由后端解析，客户端不能提交物理目录或文件名。
- 超级管理员通过既有 `admin.config` 能力修改头像目录；普通用户不能修改该配置。
- 图片响应使用 `Cache-Control: private, no-store`，保证替换后立即刷新，也不使用公开静态目录直接暴露文件。

## 验证计划

### 后端自动测试

- SQLite 初始化可重复执行，字段和配置不会重复。
- 无认证用户不能读取或上传头像。
- 用户不能通过请求参数修改其他用户头像。
- 合法 JPG、PNG、WebP 可成功保存为标准 WebP。
- 伪造扩展名、损坏图片、超限图片会被拒绝。
- 第二次上传成功后数据库引用新头像并清理旧头像。
- 文件写入或数据库更新失败时旧头像仍有效。
- 头像目录切换会复制全部引用文件；复制失败时配置不变。
- 头像文件缺失时返回无头像结果而不是服务异常。

### 前端自动与人工验证

- 未上传头像时三个位置均显示姓名首字圆形头像。
- 点击个人信息头像可以选择图片并打开圆形裁剪弹窗。
- 拖动和缩放能够改变圆形预览，取消不会修改头像。
- 保存后三个位置立即显示同一张圆形头像，无需重新登录。
- 刷新页面和重新登录后头像仍能正确加载。
- 上传错误时提示清楚且旧头像不闪烁、不丢失。
- 亮色与暗色主题下头像、悬浮层和裁剪弹窗均可正常使用。

## 验收标准

- 所有角色都能在个人信息中修改自己的头像。
- 头像裁剪和三个展示位置均保持圆形视觉效果。
- 保存后立即生效，重新登录后仍然存在。
- 用户不能修改他人头像，也不能访问物理存储路径。
- 超级管理员可配置独立头像目录，目录变更不破坏已有头像。
- 本地 SQLite 和生产 MySQL 均可自动完成兼容初始化。
- 原有登录、用户管理、权限、任务、审核和打款流程行为不变。
- 实施期间不构建安装包，不推送远程仓库。
